# 版本管理策略

## 版本号规范

本项目遵循 [Semantic Versioning 2.0.0](https://semver.org/) 规范：

```
MAJOR.MINOR.PATCH[-修饰符]
```

| 组成部分 | 含义 | 示例 |
|----------|------|------|
| MAJOR | 不兼容的 API 变更 | 1.0.0 → 2.0.0 |
| MINOR | 向后兼容的功能新增 | 0.1.0 → 0.2.0 |
| PATCH | 向后兼容的问题修复 | 0.0.1 → 0.0.2 |
| 修饰符 | 预发布/快照标识 | 0.0.1-SNAPSHOT, 0.0.1-RC1 |

### SNAPSHOT 版本

- 以 `-SNAPSHOT` 结尾，表示开发中的不稳定版本
- 可以反复部署到 snapshot 仓库，覆盖同版本号的文件
- **不可发布到 Maven Central**

### 正式版本

- 不含 `-SNAPSHOT` 后缀
- 一旦发布到 Maven Central，**不可修改、不可删除**
- 每个版本号只能使用一次

## 版本生命周期

```
0.0.1-SNAPSHOT  →  开发中
       ↓ (发布)
    0.0.1        →  正式版本 (发布到 Maven Central)
       ↓ (推进)
0.0.2-SNAPSHOT  →  下一个开发周期
```

## 分支策略

### main 分支

- 始终保持可用状态
- 版本号为 SNAPSHOT（如 `0.0.2-SNAPSHOT`）
- 所有 PR 合并到 main 前必须通过 CI

### release 流程

- 不使用单独的 release 分支
- 直接从 main 分支触发 Release 工作流
- 工作流自动完成：去 SNAPSHOT → 部署 → 打 Tag → 推进版本

### hotfix 分支（可选）

如果需要紧急修复已发布的版本：

```bash
# 从 release tag 创建 hotfix 分支
git checkout -b hotfix/0.0.1 v0.0.1

# 修复代码...

# 发布 patch 版本
# 修改版本号为 0.0.1.1 或直接跳到 0.0.2
```

## 发布节奏

| 类型 | 频率 | 说明 |
|------|------|------|
| PATCH | 按需 | Bug 修复、文档修正 |
| MINOR | 每 2-4 周 | 新功能、新模块 |
| MAJOR | 按需 | 重大架构变更、不兼容变更 |

## Tag 规范

- 格式：`v{版本号}`，例如 `v0.0.1`、`v1.0.0`
- 使用 annotated tag（`git tag -a`）
- Tag 消息：`Release v{版本号}`

## Changelog

建议维护 `CHANGELOG.md`，格式参考 [Keep a Changelog](https://keepachangelog.com/)：

```markdown
# Changelog

## [0.0.1] - 2026-08-02
### Added
- 初始版本发布
- OpenClaw Runtime SDK 核心模块
- Spring Boot 自动配置
- Skill/Tool 框架
```

GitHub Release 工作流会自动生成 release notes，但手动维护的 Changelog 更加清晰可控。
