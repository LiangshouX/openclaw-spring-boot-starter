# 第3章：认证、权限与作用域

> **学习目标**：理解 OpenClaw Gateway 的认证机制、Scope 层级、以及为什么 WebSocket 和 HTTP 的权限表现不同。

---

## 3.1 认证方式

Gateway 支持三种认证方式：

| 方式 | 配置 | HTTP | WebSocket |
|------|------|------|-----------|
| **Token** | `gateway.auth.token` | `Authorization: Bearer <token>` | `auth.token` 在 connect 请求中 |
| **Password** | `gateway.auth.password` | Basic Auth | 同上 |
| **Trusted Proxy** | `gateway.auth.mode: "trusted-proxy"` | 代理注入身份头 | — |
| **None** | `gateway.auth.mode: "none"` | 无需认证 | 仅限内网 |

SDK 使用 **Token 认证**，这是最常见的方式。

## 3.2 Scope 层级

Gateway 定义了多层权限（Scope），从低到高：

```
operator.read           ← 只读：查询状态、列表、日志
    ↑
operator.write          ← 读写：发送消息、调用工具、更新设置
    ↑
operator.admin          ← 管理员：配置变更、高权限审批
    ↑
operator.pairing        ← 设备/节点配对管理
operator.approvals      ← 执行与插件审批
operator.talk.secrets   ← 读取含密钥的 Talk 配置
```

### 各 Scope 能做什么

| Scope | 允许的操作 |
|-------|-----------|
| `operator.read` | `sessions.get`、`tasks.list`、`chat.history`、`health` |
| `operator.write` | `chat.send`、`sessions.create`、工具调用 |
| `operator.admin` | 配置变更、Gateway 重启、敏感操作 |
| `operator.pairing` | 设备配对审批、节点管理 |

## 3.3 WebSocket 的 Scope 问题

这是 SDK 开发中**最关键的发现**：

```
┌─────────────────────────────────────────────────────────┐
│                  WebSocket Scope 授予规则                 │
│                                                          │
│  连接成功 ──► hello-ok                                   │
│                └─ auth: { role: "operator", scopes: [] } │
│                                                          │
│  scopes = []  ← 空的！                                   │
│                                                          │
│  结果：                                                  │
│  ✗ chat.send → "INVALID_REQUEST: missing scope:          │
│                 operator.write"                          │
│  ✓ sessions.get → 成功（不需要特定 scope）               │
│  ✓ health → 成功                                         │
└─────────────────────────────────────────────────────────┘
```

### 为什么 WebSocket 没有 Scope？

Gateway 的设计是：**WebSocket 连接的 Scope 来自设备配对记录**。

```
普通 CLI 用户的工作流：
1. 首次连接 → 提交设备身份（公钥 + 签名）
2. Gateway 创建"待配对"请求
3. 管理员审批
4. Gateway 颁发设备令牌（device token）
5. 后续连接使用设备令牌 → 获得完整 Scope
```

**我们的 SDK 没有设备身份**，所以 Gateway 无法通过配对记录确定 Scope。

## 3.4 HTTP 端点的 Scope 优势

根据 OpenClaw 文档：

> Shared gateway token/password auth is treated as trusted operator access. OpenAI-compatible HTTP surfaces restore the normal **full operator default scope set** for shared-secret bearer auth.

翻译：**HTTP 端点使用 Token 认证时，自动获得完整 Scope**。

```
┌─────────────────────────────────────────────────────────┐
│                  HTTP Scope 授予规则                      │
│                                                          │
│  POST /v1/chat/completions                               │
│  Authorization: Bearer <token>                           │
│                                                          │
│  Gateway 自动授予：                                       │
│  ✓ operator.admin                                        │
│  ✓ operator.approvals                                    │
│  ✓ operator.pairing                                      │
│  ✓ operator.read                                         │
│  ✓ operator.talk.secrets                                 │
│  ✓ operator.write                                        │
│                                                          │
│  结果：                                                   │
│  ✓ chat.send → 成功！                                    │
└─────────────────────────────────────────────────────────┘
```

## 3.5 架构决策：双传输层

这个权限差异直接决定了 SDK 的传输架构：

```
需要 operator.write 的操作 ──► HTTP 端点
  ├─ chat.send（发送聊天消息）
  └─ 其他写操作

只需要 operator.read 的操作 ──► WebSocket RPC
  ├─ sessions.get / sessions.describe
  ├─ tasks.get / tasks.list
  ├─ chat.history
  ├─ artifacts.get / artifacts.list
  └─ 事件订阅（实时流）
```

## 3.6 设备配对（进阶）

如果未来需要让 WebSocket 也获得完整 Scope，需要实现设备配对：

```
SDK Client                          Gateway
    │                                  │
    │  ── connect (with device) ──►    │
    │      {                           │
    │        device: {                 │
    │          id: "fingerprint",      │
    │          publicKey: "...",       │
    │          signature: "...",       │
    │          signedAt: timestamp,    │
    │          nonce: "..."            │
    │        }                         │
    │      }                           │
    │                                  │
    │  ◄── pending pairing request     │
    │      (等待管理员审批)              │
    │                                  │
    │  ═══ 管理员 approve ═══          │
    │                                  │
    │  ◄── device token                │
    │                                  │
    │  ── reconnect (with token) ──►   │
    │                                  │
    │  ◄── hello-ok                    │
    │      auth: { scopes: [full] }    │
```

这需要实现密钥对生成、签名、配对审批等流程，复杂度较高。当前 SDK 通过 HTTP 端点绕过这个限制。

## 3.7 实际调试技巧

### 查看 Gateway 授予的 Scope

在 WebSocket 握手成功后，打印 `hello-ok` 中的 `auth` 字段：

```java
log.info("WebSocket connected: role={}, scopes={}",
    payload.path("auth").path("role").asText(),
    payload.path("auth").path("scopes"));
```

如果看到 `scopes=[]`，说明当前连接没有写权限。

### 测试 HTTP 端点是否可用

```bash
# 检查端点是否启用
curl -s http://gateway:13015/v1/models \
  -H "Authorization: Bearer YOUR_TOKEN"

# 如果返回模型列表，说明 HTTP 端点已启用
# 如果返回 404，需要在 Gateway 配置中启用
```

## 3.8 小结

| 知识点 | 要点 |
|--------|------|
| Token 认证 | HTTP 用 `Authorization: Bearer`，WS 用 `auth.token` |
| Scope 层级 | read < write < admin，写操作需要 `operator.write` |
| WebSocket Scope | 依赖设备配对，无配对时 `scopes=[]` |
| HTTP Scope | Shared-secret auth 自动获得完整 Scope |
| 架构影响 | 写操作走 HTTP，读操作走 WebSocket |
